# 幾何述語 (geometric predicates)

計算幾何のアルゴリズムは、座標そのものではなく**述語 (predicate) の符号**の上に成り立っています。ここでは本プロジェクトが採用する符号規約と、浮動小数点で計算することの帰結をまとめます。

対応する実装は [`src/geometry/predicates.rs`](../src/geometry/predicates.rs) です。

## 1. なぜ述語なのか

ドロネー分割のアルゴリズムが本当に必要としているのは、次の2つの問いに対する答えだけです。

1. 3点はどちら回りに並んでいるか（向き, orientation）
2. ある点は、3点が定める外接円 (circumcircle) の内側か外側か

いずれも「大きさ」ではなく「符号」の問題です。どちらも行列式 (determinant) の符号として表現できます。

この構造は重要です。アルゴリズムが符号しか使わないなら、**述語さえ正しければアルゴリズムは正しい**ことになり、数値誤差の議論を述語モジュールの中に閉じ込められます。本プロジェクトが述語を独立したモジュールに切り出しているのは、そのためです。

## 2. orient2d

```rust
pub fn orient2d(a: Point2, b: Point2, c: Point2) -> f64
```

次の行列式を計算します。

```
            | b.x - a.x   b.y - a.y |
D(a,b,c) =  |                       |
            | c.x - a.x   c.y - a.y |
```

これは三角形 `abc` の**符号付き面積 (signed area) の2倍**です。

### 符号規約

| 値 | 意味 |
| --- | --- |
| `> 0` | `a, b, c` は反時計回り (counter-clockwise, CCW) |
| `< 0` | `a, b, c` は時計回り (clockwise, CW) |
| `= 0` | 3点は共線 (collinear) |

**この規約が本プロジェクト全体の基準です。**

### 性質

- 2つの引数を入れ替えると符号が反転します（奇置換, odd permutation）。
- 巡回置換 (cyclic rotation) では値が変わりません（偶置換, even permutation）。`orient2d(a,b,c) = orient2d(b,c,a) = orient2d(c,a,b)`

## 3. incircle

```rust
pub fn incircle(a: Point2, b: Point2, c: Point2, d: Point2) -> f64
```

次の行列式を計算します。`d` を原点に移してから、放物面 (paraboloid) `z = x² + y²` へ持ち上げた形です。

```
| a.x - d.x   a.y - d.y   (a.x - d.x)² + (a.y - d.y)² |
| b.x - d.x   b.y - d.y   (b.x - d.x)² + (b.y - d.y)² |
| c.x - d.x   c.y - d.y   (c.x - d.x)² + (c.y - d.y)² |
```

### 符号規約

**`a, b, c` が CCW であるときに限り**、次を意味します。

| 値 | 意味 |
| --- | --- |
| `> 0` | `d` は外接円の**内部** |
| `< 0` | `d` は外接円の**外部** |
| `= 0` | 4点は共円 (cocircular) |

### 頂点順序と符号の関係 — 最も重要な落とし穴

`incircle` は行列式なので、`a, b, c` の向きが反転すると値の符号も反転します。

```rust
incircle(a, b, c, d) == -incircle(a, c, b, d)
```

したがって **CW の三角形に対して `incircle` を呼ぶと、内外判定が丸ごと入れ替わります。**

これが厄介なのは、失敗の仕方が静かなことです。プログラムはクラッシュせず、例外も出ません。Bowyer–Watson 法は「外接円の内部に挿入点を含む三角形」を削除して進むので、判定が反転すると、削除すべきでない三角形を削除し、削除すべき三角形を残します。結果として得られるのは、一見それらしい**間違ったメッシュ**です。

### 対策 — 呼び出し側のチェックではなく不変条件で

呼び出しのたびに向きを確認する方法は採りません。チェック漏れが1箇所でもあれば同じことだからです。代わりに、**メッシュに入る三角形は常に CCW である**という不変条件 (invariant) を維持します。

さらに重要なのは、その統一を行う**タイミング**です。

> 向きの統一は、アルゴリズムの最後ではなく、**新しい三角形を生成した瞬間**に行う。

理由は単純で、`incircle` は挿入ループの**途中**で呼ばれるからです。最後にまとめて向きを揃える実装は、次の点を挿入する時点ではまだ向きが崩れており、判定が反転します。

本実装では [`Mesh2::push_oriented`](../src/delaunay2d/mesh.rs) が三角形をメッシュに入れる唯一の経路で、そこで必ず再配向します。

## 4. 浮動小数点誤差

### 何が起きるか

どちらの述語も、まず座標の差を取ります。近接した点や、ほぼ退化した配置では、この減算で**桁落ち (catastrophic cancellation)** が起きます。有効数字が失われた値どうしを掛けて足すため、結果がゼロに近いとき、その**符号は信頼できません**。

`tests/predicates.rs` の `orient2d_loses_its_sign_near_degeneracy` は、これを実際に見せるテストです。厳密には共線な3点をわずかに（1 ulp だけ）動かすと、返る値は丸め誤差に埋もれた大きさになります。

### 本プロジェクトの方針 — 許容誤差を使わない

述語の中にも呼び出し側にも、次のようなコードは書きません。

```rust
// このプロジェクトでは書かない
if value.abs() < EPSILON {
    return 0.0;
}
```

理由は2つあります。

**1. 単一の絶対 EPSILON は理論的に無意味です。** 各述語の値は、座標の長さについて異なる次数でスケールします。

| 述語 | スケール |
| --- | --- |
| `orient2d` | 長さの2乗 |
| `incircle` | 長さの4乗 |

座標を10倍すると `orient2d` は100倍、`incircle` は10000倍になります。両方に共通で使える定数は存在せず、さらに入力のスケールが変われば適切な値も変わります。

**2. しきい値は問題を解決せず、隠すだけです。** ゼロと判定したところで、その配置が退化しているという事実は変わりません。決定的なタイブレーク規則がなければ、どちらにせよ結果は保証できません。

### 代わりにすること

**符号をそのまま使い、ほぼ退化した入力の結果は保証しないと明示します。** これは制限ですが、正直な制限です。

許容誤差はテストの検証コードにのみ存在します（[`tests/common/mod.rs`](../tests/common/mod.rs)）。そこで比較するのは面積のような本質的に近似的な量であり、**トポロジーを決めることはありません**。この2種類の許容誤差を同じ定数で兼用しないことが重要です。

### 「保証しない」の実際の範囲

軽く見られがちなので、具体例を挙げます。

正六角形の6頂点は厳密に同一円周上にあります。この入力に中心点を加えて分割すると、**三角形が1つ欠けた結果**になります。すべての外周三角形が同じ外接円を持つため `incircle` がゼロではなく丸め誤差を返し、そこから作られる空洞がアルゴリズムの前提とする星形領域 (star-shaped region) にならないからです。

半径を `1e-15` ずらして厳密な共円性を崩すと、6個そろいます。つまりこれはアルゴリズムの誤りではなく、`f64` 述語の限界です。

`tests/degeneracy.rs` にこの両方をテストとして残してあります。

## 5. exact arithmetic / adaptive precision

上の制限を根本的に解消する方法は、述語を**厳密に**評価することです。

- **exact arithmetic**: 多倍長で計算し、常に正しい符号を得る。確実だが遅い。
- **adaptive precision**: まず `f64` で計算し、誤差限界と比較して符号が確定できれば即座に返す。確定できない場合にのみ精度を上げる。Shewchuk の手法がこれで、大半の入力では `f64` とほぼ同じ速度になります。

Rust では [`robust`](https://crates.io/crates/robust) クレートが Shewchuk の述語を提供しています。本実装は関数シグネチャをこれに合わせてあるため、差し替えは述語モジュールの中だけで完結します。

ただし注意すべきは、**robust predicate は数値の問題しか解決しない**ことです。4点が本当に共円である配置でドロネー分割が一意でないことは、精度とは無関係な幾何的事実です。一意な結果が必要なら、Simulation of Simplicity のような記号的なタイブレーク規則を別途導入する必要があります。

本プロジェクトの [退化入力に対する契約](../README.md#退化入力に対する契約-contract) が、数値的な理由（ほぼ共線・ほぼ共円）と、原理的な曖昧さ（厳密な共円、辺上の点）を分けて書いているのは、この2つが別の問題だからです。

## 6. 3D の述語について

`orient3d` と `insphere` は未実装です。実装時には同じ構造の規約を定めます。

- `orient3d(a,b,c,d) / 6` を符号付き体積 (signed volume) とし、正を「正の向き」と定義する
- `insphere` は四面体 `abcd` が正の向きのときにのみ「正 = `e` が外接球 (circumsphere) の内部」を意味する

3D では追加の落とし穴があります。共有面 (face) の数を数えるために節点番号をソートしたキーを使いますが、**ソート済み表現は面の向きを保持しません**。新しい四面体を作るときに元の面の節点順序をそのまま使うと向きが壊れるため、必ず `orient3d` で再配向する必要があります。
